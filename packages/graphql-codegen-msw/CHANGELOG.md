## 0.1.0

### Minor Changes

- [#91](https://github.com/softistx/nxgt-graphql/pull/91) [`55c1ea2`](https://github.com/softistx/nxgt-graphql/commit/55c1ea2cc4d3f32afbf9468daf71d516d4704ea6) Thanks [@SteveGT96](https://github.com/SteveGT96)! - The first release: a graphql-codegen plugin that writes one typed msw 3 handler per named query and mutation, `mockUserQuery(resolver, options?)`, built on msw's `graphql.link(endpoint)`. The resolver is msw's own, its `variables` typed with the operation's variables type and its `data` with the result type, both imported from `typesImport` (the client preset's `graphql.ts`, or `typescript-operations`' file). Each handler checks its variables with `@nxgt/graphql-codegen-zod`'s `z<Operation>Variables` (`schemasImport`) before the resolver runs, and answers an invalid input without calling it. A value the API refuses while coercing the variables (a missing or `null` value for a non-null type, a wrong type, an unknown enum value or input field, an Int beyond 32 bits, a value a custom scalar refuses) is answered first, as graphql-yoga 5.24 on graphql 17 answers it, whatever `invalidInput` is: status 400, one plain `{ message, locations }` error per problem in graphql 17's wording and order, every type named and graphql's "Did you mean …?" included, no `extensions`. The plugin reads the schema for it: the generated file carries the input types the variables reach and each variable's type (`inputTypes`, `variableTypes`, an internal shape), and the handler walks the variables as graphql does, a custom scalar refusing where its Zod schema does. Checked against a graphql-yoga server over 75 requests, 74 answered identically, values printed as graphql and the executor each print them; the known differences, listed in the handlers guide, are an `ID` given an integer (the probe's one difference), a custom scalar not built with `zodScalar`, an application format's code, and an API on graphql 16. A handler written by hand with `mockOperation` may leave out `variableTypes` and `inputTypes`: every refusal then goes to `invalidInput`. Any other invalid input, a constraint, is answered by default as one 400 error with a list of fields (`invalidInputError` from `@nxgt/graphql-validation`, a field per Zod issue through its `fieldIssueOf`, its path starting at the variable's name, its code `validation.errors.too-short`, `too-long`, `out-of-range`, `too-few`, `too-many`, `invalid-format` (a format or a pattern) or `invalid` (anything else, a prefix, suffix or substring included), no params; `translate: '<module>#<export>'` for the messages), with `invalidInput: 'bad-user-input'` as the `BAD_USER_INPUT` error `withValidation` raises, or with `invalidInput: '<module>#<export>'`, a function of yours returning `{ error, status }`. A `GraphQLError` the resolver throws is answered at its `extensions.http.status`; `errorResponse(error, { status })` builds the same answer. As graphql-yoga does, every body leaves out `extensions.http` and `extensions.unexpected`, several errors answer at the highest status among them, and a status no response can carry (outside 200–599, or 204, 205, 304), from an error or from `invalidInput`, is ignored. `endpoint` is required and overridable per handler (`options.endpoint`), beside msw's `once`. The generated file's runtime is the `./runtime` subpath: `mockOperation`, `invalidInputRefusal`, `badUserInputRefusal`, `errorResponse`, `isGraphQLError`, and the internal `InputTypes` and `InputType` types the generated file annotates with; it re-exports `@nxgt/graphql-validation`'s `invalidInputError`, `fieldsError`, `fieldIssueOf`, `inputPath` and the types `Translate`, `FieldIssue`, `FieldError`, so a function of your own imports them from `@nxgt/graphql-codegen-msw/runtime`. Depends on `@nxgt/graphql-validation` `^0.4.0`: an application that imports it itself needs `^0.4.0` too. The coercion code ported from graphql-js and graphql-tools is MIT-licensed, its notices in `THIRD-PARTY-NOTICES.md`. Peers: `msw` `^3.0.3`, `graphql`, `zod`, `typescript`. Subscriptions, persisted queries and batching are on the roadmap.
